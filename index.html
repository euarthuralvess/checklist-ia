Secure by Design
para Devs com IA

20 verificações essenciais antes de colocar qualquer feature com IA em produção. Cada item é uma vulnerabilidade real já explorada em ambientes de produção.

01 — Exposição de Dados
Commits sem API keys, tokens ou credenciais CRÍTICO
Use git-secrets ou trufflehog antes de cada push. Um repositório público com key exposta é comprometido em média em 4 minutos.
README não descreve arquitetura interna, IPs ou stack de produção ALTO
LLMs mapeiam vetores de ataque a partir de documentação pública. Documente o necessário, não o suficiente para um atacante.
LinkedIn e GitHub não expõem versões exatas de tecnologias em uso MÉDIO
Ex: "Spring Boot 2.5.4" em um post é input direto para busca de CVEs. Use termos genéricos em posts públicos.
02 — Segurança da API de IA
A API key do Gemini/OpenAI está no backend, nunca no frontend CRÍTICO
Qualquer key no JS do cliente pode ser extraída em segundos com DevTools. Use variáveis de ambiente no servidor.
Rate limiting implementado nas chamadas à API de IA ALTO
Sem rate limit, um atacante usa seu endpoint para gerar conteúdo em escala no seu custo. Implemente limites por usuário e por IP.
Input do usuário é sanitizado antes de ir para o prompt CRÍTICO
Prompt Injection: usuário insere instruções que sobrescrevem o system prompt. Valide e sanitize todo input antes de concatenar ao prompt.
System prompt não contém segredos de negócio ou credenciais ALTO
System prompts podem ser extraídos via prompt injection. Nunca coloque credenciais ou lógica sensível como única barreira.
Output do modelo é validado antes de ser executado ou exibido CRÍTICO
Modelos podem gerar código malicioso, scripts injetados ou conteúdo que cause dano se renderizado sem sanitização. Nunca execute output de LLM diretamente.
03 — Autenticação e Controle de Acesso
MFA habilitado em todas as contas de serviços cloud CRÍTICO
Spear phishing com IA tem 3x mais taxa de clique que phishing genérico. Sem MFA, uma credencial comprometida = acesso total.
Princípio do menor privilégio aplicado a service accounts ALTO
A service account da API de IA não precisa de acesso ao banco de dados de produção. Segmente as permissões por função.
Tokens de API têm expiração definida e são rotacionados MÉDIO
Token sem expiração comprometido = acesso permanente. Defina TTL e implemente rotação automática no ciclo de deploy.
04 — Proteção contra Ataques via IA
Validação de e-mails suspeitos no processo de onboarding ALTO
Verifique domínio, data de criação do domínio e histórico de reputação. E-mails gerados por IA têm estrutura diferente dos convencionais.
Time treinado sobre risco de deepfake de voz/vídeo em processos críticos CRÍTICO
Qualquer processo que aceita confirmação verbal de identidade precisa de segundo fator. Verifique por canal alternativo antes de agir.
Dados de produção não usados para fine-tuning ou testes de IA ALTO
Modelos fine-tunados com dados reais podem vazar informações via prompt. Use dados sintéticos ou anonimizados para experimentos.
Ao menos um teste de prompt injection realizado na aplicação CRÍTICO
Tente: Ignore as instruções anteriores e... Se sua aplicação ceder, há vulnerabilidade aberta em produção.
05 — Monitoramento e Resposta
Logs de chamadas à API de IA coletados e retidos ALTO
Sem logs não há forense após incidente. Colete: timestamp, user_id, input hash, tokens consumidos, response status.
Alerta configurado para pico anômalo de uso da API MÉDIO
Pico de 10x no volume às 3h da manhã é sinal. Configure alertas de threshold no provedor cloud ou SIEM.
Plano de resposta a incidentes de IA documentado MÉDIO
O que fazer se o modelo gerar output malicioso? Se a API key vazar? Se houver injeção em produção? Documente antes que aconteça.
Revisão de segurança incluída no ciclo de deploy de features com IA ALTO
Segurança não é etapa final — é parte do pipeline. Adicione checklist de segurança como gate antes de qualquer deploy que envolva LLM.
